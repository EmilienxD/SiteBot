# Application tools

Every tool is owned by the consuming application. SiteBot validates complete registrations and model arguments, normalizes model-facing schemas, invokes the registered handler or transport, validates its result, and continues the bounded loop. No code generated by the model is evaluated. No builtin tool catalog or fallback browser implementation exists.

```ts
import { defineConfig } from '@sitebot/config'
import type { ToolHandler } from '@sitebot/core'

const readStatus: ToolHandler = (_input, ctx) => ({ locale: ctx.locale, status: 'available' })

export default defineConfig({
  version: 1,
  name: 'Status assistant',
  backend: { provider: 'openai', model: 'application-selected-model' },
  prompt: { system: 'Help visitors understand application status.' },
  tools: [{
    name: 'read_status',
    description: 'Read the application status in the visitor locale.',
    parameters: { type: 'object', additionalProperties: false },
    outputSchema: { type: 'object', properties: { locale: { type: 'string' }, status: { type: 'string' } }, required: ['locale', 'status'], additionalProperties: false },
    execute: readStatus,
    readOnly: true,
    scope: 'public',
    requiresApproval: false,
    timeoutMs: 3000,
  }],
})
```

Exactly one `execute` or `executor` is required. Input uses an object-root JSON Schema or native Zod object schema; output uses JSON Schema or native Zod. Ajv enforces constraints and rejects unsupported definitions. Native Zod validation retains transforms and refinements. Invalid arguments never reach the handler or hook. Invalid, non-JSON or late output fails safely. Each admitted call has a private cooperative abort signal and a scoped source registrar.

## Transports

- `http`: the application declares URL, method, headers/body mapping, host allowlist, response limits and optional response path. Node hosts use SSRF-hardened fetching. Model-controlled parameters cannot rewrite hosts or trusted headers.
- `module`: the application declares a module path and export. The export is the application implementation.
- `mcp`: the application declares one exact remote `tool`, server transport, description, input/output schemas and permissions. Wildcards and bulk discovery are rejected. Remote catalog descriptions never supply trusted instructions or registrations.
- `client`: the application declares an implementation `id` and registers it using `SiteBot.registerTool(id, handler)` or the element/controller API. The widget verifies the server's tool-name allowlist, resolves the declared id and calls only that registered application handler. Missing handlers fail; no navigation, DOM access, form fill, clipboard or vendor action is supplied automatically.

## Permissions and lifecycle

Chat mode exposes only read-only tools. Authenticated tools require verified identity. Writable agent tools should require user approval. Approval records bind the exact call and expire with their checkpoint. Unknown/disabled/unauthorized/unapproved/resumed/final-step forged calls cannot invoke hooks or handlers. `onToolCall` is observational: returned values are ignored. Tool deadlines and output validation apply to actual handler execution. Session call caps require atomic store claims; unsupported stores fail closed.

Application tool names such as `search_knowledge_base` or `read_document` are ordinary names with no reserved behavior. Applications implement any search, reading, ingestion or actions themselves. Empty registries remain empty.

## Application sources and citations

A successful server handler can call `ctx.sources.register({ id, title, url, text, lang? })`, receiving `{ n, id }`. See [source provenance](06-sources.md). Returning URLs or citation-shaped tool data alone never grants provenance.
